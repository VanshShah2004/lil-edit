  Search Autosuggestions & Results — How it Works

  Autosuggest flow: SearchBar.tsx → SearchPanel.tsx → useSearchSuggestions.ts
  (300ms debounce) → GET /api/products/suggestions → fetchSuggestions() in
  backend/lib/persistCatalog.ts → rendered by SuggestionsDropdown.tsx.

  Search results flow: SearchResults.tsx → GET /api/products/search →
  searchProducts() in persistCatalog.ts. Client-side then applies filters
  (category/badge/price/stock) and sort — "relevance" just passes through the
  backend's order untouched; price-asc/desc re-sorts numerically.

  Scoring ("point system") — all in-process TypeScript, no DB full-text search:

  1. scoreEntry() (persistCatalog.ts) scores every catalog product against the
  query with tiered FIELD_SCORES:
    - title:exact=100, title:starts=90, title:word-starts=85, title:contains=80,
  category:starts=78, category=75, tag:starts=72, tag=65, occasion:starts=63,
  occasion=60, badge:starts=58, badge=55, fabric:starts=53, fabric=50,
  fit:starts=50, fit=48, gender=45, fuzzy(Levenshtein)=30
    - Fields checked in priority order (title wins over category wins over tag,
  etc.)
    - Within a tier, matchQuality() adds a 0–1.9 bonus (coverage×1.4 + 
  position×0.5) — tighter/earlier matches rank higher without crossing into the
  next tier
  2. searchLexicon.ts — a curated ~140-term list (categories, occasions,
  fabrics, fits, colors, trends, keywords) independent of live inventory, each
  with a static admin-set weight (0–20, acts as a popularity boost). Match
  types: exact=100, prefix=90, wordPrefix=84, contains=76, fuzzy=34, alias -4
  penalty. Final score = matchScore + weight.
  3. Merge: product-derived suggestions and lexicon matches are merged by label;
  on collision, higher score wins. Suggestions capped at 8 products + 8
  metadata chips. Full results page uses the same scorer but uncapped, one card
  per color variant.
  4. Tiebreak everywhere: descending score, then alphabetical.

  Caching: Redis caches both endpoints by query string; the in-memory product
  catalog itself is cached 10 minutes, invalidated on publish/delete.

  No dynamic popularity/recency ranking — there's no click-through,
  purchase-count, or recency signal feeding into scores. The only "popularity"
  proxy is the hardcoded lexicon weight. Search queries are logged to the
  activity feed for analytics, but that data doesn't loop back into ranking.

     Title-First Search Ranking

     Context

     The search scoring engine (backend/lib/persistCatalog.ts) currently ranks
     all matches on a single numeric point ladder (FIELD_SCORES: title:exact=100
     … fuzzy=30). Title matches usually win because their scores are highest,
     but they compete on the same axis as category/tag/badge/etc. The user wants
     title matches structurally guaranteed to appear first — as a separate
     bucket above the point ladder — not merely by having bigger numbers. Both
     /api/products/suggestions and /api/products/search share this engine, so
     one change covers the dropdown and the results page.

     Approach

     Return an explicit title rank from the scorer, then sort by (title rank →
     score → stock breadth → title). No frontend changes — the frontend already
     preserves backend order for "relevance".

     1. scoreEntry() returns a title rank (persistCatalog.ts ~line 958)

     Extend the return type to { score: number; field: string; titleRank: number
     }:

     ┌───────────────────────────────────────────────────────┬─────────────────┐
     │                         Match                         │    titleRank    │
     ├───────────────────────────────────────────────────────┼─────────────────┤
     │ title exact                                           │ 0               │
     ├───────────────────────────────────────────────────────┼─────────────────┤
     │ title starts-with                                     │ 1               │
     ├───────────────────────────────────────────────────────┼─────────────────┤
     │ title word-starts-with                                │ 2               │
     ├───────────────────────────────────────────────────────┼─────────────────┤
     │ title contains                                        │ 3               │
     ├───────────────────────────────────────────────────────┼─────────────────┤
     │ everything else                                       │ 4               │
     │ (category/tag/occasion/badge/fabric/fit/gender/fuzzy) │ (NO_TITLE_MATCH │
     │                                                       │  constant)      │
     └───────────────────────────────────────────────────────┴─────────────────┘

     Fuzzy stays in the non-title bucket (requirement 2 lists it with the
     point-based fields). Numeric FIELD_SCORES values stay untouched — they
     still order results within each bucket, so metadata suggestion scoring
     (lines 1042–1088), lexicon merging, and matchQuality are unaffected.

     2. Shared comparator + stock breadth

     Add near scoreEntry:

     // In-stock variant count; a variant-less product renders one in-stock 
     card.
     function stockBreadth(entry: SearchCatalogEntry): number {
       if (entry.variants.length === 0) return 1;
       return entry.variants.filter(v => v.inStock).length;
     }

     function compareRanked(a, b) {
       return a.titleRank - b.titleRank          // title bucket + subtype order
     (0–3 before 4)
         || b.score - a.score                    // point ladder within bucket
         || stockBreadth(b.entry) - stockBreadth(a.entry) // broader 
     availability first
         || a.entry.title.localeCompare(b.entry.title);
     }

     titleRank ascending alone satisfies both "title bucket first" and "subtype
     order" (0,1,2,3 all sort before 4).

     3. Apply in both consumers

     - fetchSuggestions() line ~1025–1030: store titleRank in scored, replace
     the sort with scored.sort(compareRanked). Metadata derivation (upsertMeta)
     is order-independent (keeps max score per key) — unchanged. Product cap of
     8 and metadata cap of 8 unchanged.
     - searchProducts() line ~1171–1176: same — store titleRank, sort with
     compareRanked. Variant flattening unchanged.

     4. Inclusion threshold (requirements 5 & 6)

     Nothing is suppressed: all matches (title and non-title) stay in the result
     set. Make requirement 6 explicit with a named constant MIN_RESULT_SCORE = 
     25 and filter score > MIN_RESULT_SCORE instead of score > 0 — behaviorally
     identical today (the lowest possible match score is fuzzy=30) but encodes
     the contract.

     5. Tests

     Backend test pattern exists: node:test + assert/strict, run via tsx
     (backend/test/mailer.test.ts, script "test" in backend/package.json).

     - Export scoreEntry, compareRanked (and NO_TITLE_MATCH/MIN_RESULT_SCORE)
     from persistCatalog.ts (module has no top-level side effects; requireAdmin
     is lazy, so importing it in tests is safe).
     - New backend/test/searchRanking.test.ts with synthetic SearchCatalogEntry
     fixtures covering:
       - a title:contains match (score ~80+q) outranks a category:starts match
     (78+q) AND a hypothetical high-score non-title match — bucket beats points
       - title subtype order: exact > starts > word-starts > contains
       - non-title matches (incl. fuzzy) still present after the title group,
     ordered by score
       - stock-breadth tiebreak between equal-score entries, then alphabetical
     - Add the new file to the test script in backend/package.json.

     Files to modify

     - backend/lib/persistCatalog.ts — scorer return type, comparator, two sort
     sites, exports
     - backend/test/searchRanking.test.ts — new
     - backend/package.json — test script

     Verification

     1. cd backend && npm run build (tsc --noEmit) — type-check.
     2. npm test — existing + new ranking tests.
     3. Live check: hit GET /api/products/suggestions?q=... and
     /api/products/search?q=... with a query that matches one product's title
     mid-word and another product's category prefix — the title match must come
     first even though category:starts (78) can beat title:contains (80) only
     narrowly today. Note: Redis caches both endpoints by query — use a fresh
     query string or flush the cache, or old rankings will be served until TTL
     expiry.
