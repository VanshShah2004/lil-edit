  TL;DR

  The architecture, security posture, and nearly all of the analysis math are
  correct — but there is one real bug that will break 3 of the 13 pages: the SQL
  RPCs reference products.total_stock, a column you dropped back in May. Since
  the migrations haven't been run in Supabase yet, this is catchable now.
  Everything else ranges from correct to minor nits. Both apps typecheck clean,
  and the uncommitted changes are pure UI polish with no logic impact.

  How the flow works (verified end-to-end)

  Capture: The storefront mints a non-PII visitor id (localStorage), and
  TrackingBridge under the router records every route change. A PDP mount fires
  one view beacon per variant (10s dedupe defeats StrictMode double-mounts),
  with the visit source derived from the previous route
  (search/home/wishlist/etc.). A 30s heartbeat (visible tabs only, /admin
  excluded) upserts live_presence. Beacons respond 204 before touching the DB,
  validate silently, and no-op gracefully pre-migration. Cart/wishlist removes,
  increment re-adds, and checkout_started are logged from app code —
  deliberately, so size-merges, self-heals, and post-checkout clears don't
  pollute intent data. Both tables are RLS-locked with zero policies; browsers
  can neither read nor forge rows.

  Aggregation: One SQL function per page returns the full payload as jsonb.
  Every function uses active = status <> 'cancelled', guards every division with
  NULLIF, buckets in IST with zero-filled series, and takes an equal-length
  previous window for comparison. EXECUTE is revoked from anon/authenticated and
  granted only to service_role. There are no refund metrics anywhere —
  cancellations only, per your standing rule.

  Serving: /api/admin/analytics/* sits behind requireAuth + requireAdmin,
  validates/clamps the date window (max 400 days), caches 60s in Redis, and
  returns an actionable 503 naming the exact migration file if one is missing.
  The User Activity feed whitelist correctly keeps the analytics-only event
  kinds out.

  UI: All 13 routes are AdminRoute-wrapped lazy chunks. I checked the KPI wiring
  on every page against the RPC output keys — all match 1:1, with correct
  "lower is better" delta flips (cancellations, removes, discounts), "No data
  yet" instead of misleading zeros for view-based metrics, and the insight rules
  are threshold-guarded so they don't fire on noise. CSV export is properly
  RFC-4180 escaped and exports the full filtered set, not just the visible page.

  The blocker: products.total_stock no longer exists

  20260517_drop_product_total_stock.sql dropped that column (stock is
  variant-only now — CHECKOUT_PLAN.md even documents this), but three RPCs still
  read it. PL/pgSQL doesn't validate table columns at CREATE FUNCTION, so the
  migrations will apply without any error — the failure only appears when an
  admin opens the page, as a 500 (column p.total_stock does not exist):

  RPC: analytics_products
  Where: 20260712…core.sql:663
  What breaks: The whole Products page
  ────────────────────────────────────────
  RPC: analytics_product
  Where: 20260713…detail.sql:70
  What breaks: The whole per-product deep-dive (all 12 tabs, health score,
    restock/OOS insights)
  ────────────────────────────────────────
  RPC: analytics_inventory
  Where: 20260713…detail.sql:1117–1120, 1139, 1153
  What breaks: The whole Inventory page

  The ironic part: analytics_inventory's own KPI block already computes stock
  the right way (joining product_variants and summing v.stock) — only its
  fastest/slowest tables and the other two functions use the dead column. The
  fix is to derive per-product stock from variants everywhere (SUM(v.stock) with
  is_unlimited handling, since unlimited variants have NULL stock). This must
  land in the migration files before you run them in Supabase.

  Minor findings (not blockers)

  - The 60s Redis cache almost never hits. Presets compute to = now + 60s at
  page mount, so every visit produces a unique cache key. Harmless at your
  traffic level, but rounding to up to the next minute in analyticsApi.ts would
  make the cache actually work.
  - A wording nit: ProductDetail's "Avg time view → cart" hint says "Median
  time…" but the SQL computes a mean (AVG).
  - LIMIT without inner ORDER BY in the products table (500) and wishlist/cart
  tables (300) — if you ever exceed those row counts, which rows survive is
  arbitrary. Irrelevant at current catalog size.
  - Two attribution semantics worth knowing when you read the numbers:
  wishlist/cart "purchased" counts a conversion even if the order happened after
  the selected window ("eventually converted"); and Search "conversion" is any
  order within 24h of a search by that user, not necessarily a searched product.
  Both are reasonable and the UI hints describe them honestly.
  - The donut chart palette repeats after 8 categories (cosmetic; format.ts says
  callers should fold extras into "Other" but none do).

  Also verified: the seed script is safe (preflight-checks all tables, resets
  only its own batch, never touches real carts/orders), and the funnel's
  checkout_started coverage is complete because every checkout — cart or buy-now
  — passes through /initiate.
